# ใบสถานการณ์จำลอง หน่วยที่ 1 / สัปดาห์ที่ 1

- **รหัสวิชา:** 31901-2005
- **วิชา:** การพัฒนาซอฟต์แวร์ด้วยเทคโนโลยี Back-End (สอนครั้งที่ 1)
- **หน่วยการเรียนรู้:** พัฒนาบริการ API พื้นฐานและจัดการ Endpoint (ทฤษฎี 1 ชม. / ปฏิบัติ 4 ชม.)
- **เรื่อง:** ระบบแจ้งซ่อมคอมพิวเตอร์และอุปกรณ์ของวิทยาลัย
- **ใช้ในขั้น:** A, B ของสัปดาห์ที่ 1

## 1. สถานการณ์

วิทยาลัยแห่งหนึ่งมีห้องปฏิบัติการคอมพิวเตอร์ 8 ห้อง รวมเครื่องคอมพิวเตอร์ประมาณ 300 เครื่อง ใช้สอนนักศึกษาทุกวัน
ปัจจุบันเมื่อเครื่องเสียหรือใช้งานไม่ได้ ผู้ใช้จะแจ้งผ่านกลุ่มไลน์ของแผนก หรือเขียนใส่กระดาษแล้วฝากไว้ที่ห้องช่าง

ผลที่เกิดขึ้นคือ

- ข้อความในไลน์ถูกข้อความอื่นทับจนช่างไม่เห็น
- บางเรื่องมีคนแจ้งซ้ำหลายคน
- ช่างไม่ทราบว่าเครื่องไหนเคยเสียมาแล้วกี่ครั้ง
- ผู้แจ้งไม่รู้ว่างานของตนซ่อมถึงไหน
- หัวหน้างานต้องนั่งนับจากกระดาษเมื่อต้องทำรายงานสรุปประจำเดือน

วิทยาลัยจึงตัดสินใจพัฒนา "ระบบแจ้งซ่อม" ขึ้น โดยให้ทีมนักพัฒนา Back-End ออกแบบและสร้างบริการหลังบ้านก่อน
เพื่อให้หน้าเว็บและแอปบนมือถือเรียกใช้ผ่าน API ในภายหลัง

## 2. ความต้องการจากผู้เกี่ยวข้อง

จากการสัมภาษณ์ผู้เกี่ยวข้อง ได้ข้อมูลดังนี้

| ผู้เกี่ยวข้อง | สิ่งที่บอกว่าต้องการ |
|---|---|
| นักศึกษาและครูผู้สอน (ผู้แจ้ง) | "อยากบอกว่าเครื่องไหนในห้องไหนเสีย พร้อมอาการ แล้วกลับมาดูได้ว่าช่างรับเรื่องหรือยัง ซ่อมเสร็จหรือยัง และอยากดูประวัติที่เคยแจ้งไว้ ถ้าแจ้งผิดหรือไม่ต้องการแล้ว ขอยกเลิกได้ถ้าช่างยังไม่รับเรื่อง" |
| ช่างเทคนิค | "อยากเห็นรายการงานที่รอซ่อมทั้งหมด เลือกรับงานได้ แล้วอัปเดตสถานะเป็นกำลังซ่อม รออะไหล่ หรือซ่อมเสร็จ พร้อมบันทึกว่าแก้ไขอะไรไป และอยากรู้ประวัติการซ่อมเดิมของเครื่องนั้นก่อนลงมือ" |
| หัวหน้างานอาคารสถานที่และคอมพิวเตอร์ | "อยากดูสรุปว่ามีงานค้างกี่เรื่อง ซ่อมเสร็จกี่เรื่อง แยกตามห้องได้ไหม อยากมอบหมายงานด่วนให้ช่างคนใดคนหนึ่งได้ และต้องเพิ่มหรือแก้ข้อมูลห้องและเครื่องเองได้เมื่อมีการย้ายหรือซื้อเครื่องใหม่" |

## 3. กติกาและข้อจำกัดของระบบ

- ผู้ใช้ทุกกลุ่มต้องเข้าสู่ระบบก่อนทำรายการใด ๆ
- การแจ้งซ่อม 1 ครั้ง ระบุเครื่องคอมพิวเตอร์ได้ 1 เครื่อง ส่วนเครื่องหนึ่งเครื่องมีประวัติการแจ้งซ่อมได้หลายครั้ง
- งานซ่อม 1 งาน มีช่างรับผิดชอบได้ครั้งละ 1 คน
- คำขอที่ช่างรับเรื่องแล้ว ผู้แจ้งยกเลิกเองไม่ได้
- สถานะของงานมี 4 แบบ: รอดำเนินการ, กำลังซ่อม, รออะไหล่, ซ่อมเสร็จ

**อยู่นอกขอบเขตรอบนี้:** การสั่งซื้ออะไหล่ การคิดค่าใช้จ่าย การพิมพ์ใบแจ้งซ่อมกระดาษ และการออกแบบหน้าจอ

## 4. งานที่ต้องทำจากสถานการณ์นี้

ทำตามลำดับ ผลงานทุกข้อต้องสอดคล้องกัน และใช้ต่อในการจัดทำโปรเจกต์ขั้นถัดไป

| ข้อ | งาน | ผลที่ส่ง |
|---|---|---|
| 1 | อ่านสถานการณ์ แล้วขีดเส้นใต้ ผู้ใช้ระบบ สิ่งที่ระบบต้องทำ และข้อมูลที่ระบบต้องจำ | ใบสถานการณ์ที่ขีดเส้นใต้แล้ว |
| 2 | เขียนรายการความต้องการเชิงฟังก์ชัน (FR) ไม่น้อยกว่า 8 ข้อ รหัส FR-01 เป็นต้นไป ขึ้นต้นด้วย "ระบบต้อง…" และระบุว่าใครเป็นผู้ใช้ | ตาราง FR |
| 3 | วาด Use Case Diagram ให้ครบทั้ง Actor ทุกกลุ่ม พร้อมกรอบระบบ และใช้ «include» อย่างน้อย 1 แห่ง | ไฟล์ usecase.png และ .drawio |
| 4 | วาด Class Diagram อย่างน้อย 4 Class พร้อมแอตทริบิวต์และเมธอดหลัก | ไฟล์ class-diagram.png และ .drawio |
| 5 | ใส่ชื่อความสัมพันธ์และ Multiplicity ทุกเส้น แล้วตรวจว่า FR ทุกข้อมี Use Case รองรับ และทุก Use Case ใช้ Class อย่างน้อย 1 Class | แผนภาพที่แก้ไขแล้ว + ตารางตรวจสอบ |

## คำถามนำสำหรับทำแผนผังมโนทัศน์ (ขั้น A)

1. ถ้าเครื่องหนึ่งเสียซ้ำ 3 ครั้ง ระบบต้องเก็บอะไรไว้เพื่อให้ช่างรู้ประวัติ
2. ใครบ้างที่ "เห็น" หรือ "เปลี่ยน" สถานะของงานซ่อม และแต่ละคนทำได้ต่างกันอย่างไร
3. ข้อมูลอะไรที่ต้องมีก่อน จึงจะแจ้งซ่อมได้ (ห้อง เครื่อง ผู้ใช้ ฯลฯ) และข้อมูลแต่ละอย่างเกี่ยวข้องกันอย่างไร
4. ถ้าวันหนึ่งมีแอปมือถือมาเรียกใช้ระบบนี้ด้วย ส่วนไหนของระบบที่ต้องเปิดให้ภายนอกเรียกใช้
